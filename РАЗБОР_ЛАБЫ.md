## 0. Что делает программа и как устроен проект

Оконное приложение (JavaFX), электронная очередь поликлиники. Талоны хранятся в собственной двоичной min-куче, таблица показывает её содержимое, а панель под таблицей рисует дерево кучи. Можно:
- **добавить** талон (обычный или «вызов на дом») и **изменить** выбранный (кроме закрытого);
- **загрузить** талоны из CSV и **сохранить** в CSV (битые строки пропускаются, о них выводится предупреждение);
- **слить** очередь с CSV-файлом как со второй очередью;
- **извлечь минимум**, **найти** по номеру карты, **удалить**, показать **Top-K**, **изменить приоритет**;
- **сгенерировать** N случайных талонов в фоне, с прогрессом и отменой;
- посмотреть **демонстрацию гонки** потоков;
- сделать **экспорт и импорт** в форматах `.bin` и `.json`.

Есть три вида талонов (иерархия наследования):

```
                 Ticket  (абстрактный: общие поля, геттеры, validateCommon)
                ▲      ▲ extends
     RegularTicket     ClosedTicket
     (обычный,         (закрытый, только чтение, "CLOSED",
      "TICKET",         не Editable, сеттеров нет)
      implements Editable, сеттеры)
                ▲ extends
     HomeVisitTicket
     (вызов на дом, "HOME", плюс адрес)
```

Структура пакетов — по принципу разделения ответственности (похоже на MVC):

| Пакет | Роль | Классы |
|---|---|---|
| `app` | точка входа, запуск окна | `Main`, `ClinicApplication` |
| `model` | данные + проверка данных (Model) | `Ticket`, `RegularTicket`, `HomeVisitTicket`, `ClosedTicket`, `Editable`, `TicketType` |
| `structure` | своя структура данных | `TicketHeap`, `SynchronizedTicketHeap` |
| `service` | логика без GUI | `TicketGenerator`, `RaceDemo` |
| `csv` | работа с CSV | `CsvFormat`, `CsvLoader`, `CsvSaver`, `CsvLoadException`, `CsvErrorCode` |
| `serialization` | форматы bin и JSON | `Serializer`, `Serializers`, `BinarySerializer`, `JsonSerializer`, `TicketDto`, `SerializationException`, `SerializationErrorCode` |
| `controller` | окно, таблица, диалоги (View + Controller) | `MainController`, `FileActions`, `QueueTasks`, `TaskPanel`, `HeapCanvas`, `TicketTableFactory`, `TicketDialog`, `Dialogs` |

Путь `src/main/java/...` — стандартная структура Maven: исходники Java лежат именно там. Тесты, фикстуры и бенчмарки лежат в `src/test`.

## 1. Шпаргалка по ключевым словам Java

### Модификаторы доступа (кто может видеть класс/поле/метод)

| Модификатор | Где виден | Пример в лабе |
|---|---|---|
| `public` | везде | `public abstract class Ticket`, все геттеры и сеттеры |
| `protected` | в своём пакете + в наследниках | `protected String cardNumber;` в `Ticket`: в поле пишут сеттеры наследника |
| *(ничего)* — package-private | только внутри своего пакета | `record TicketDto`, `BinarySerializer.MAGIC` |
| `private` | только внутри этого класса | `private T[] items;`, `private CsvFormat() {}` |

Снаружи к полям обращаются только через `public` методы. Это **инкапсуляция**: нельзя напрямую испортить поле, только через методы, которые класс контролирует (например, у `ClosedTicket` сеттеров нет вообще, а массив кучи никто не видит снаружи).

### `static`

`static` = «принадлежит **классу**, а не конкретному объекту».

- **static-поле** — одна переменная на весь класс, общая для всех объектов. Пример: `Ticket.PRIORITY` — компаратор один на всю программу, для него не нужен объект талона.
- **static-метод** — вызывается через имя класса, без создания объекта: `Dialogs.error(stage, "...")`, `TicketDialog.showForCreate(stage)`, `Integer.parseInt(...)`. Внутри static-метода **нет `this`**, поэтому нельзя обращаться к обычным (нестатическим) полям объекта.
- **`public static void main(String[] args)`** — `main` обязан быть static, потому что JVM вызывает его ещё до того, как создан хоть один объект.
- **static вложенный тип** — `record LoadResult` внутри `CsvLoader` неявно static: ему не нужен объект `CsvLoader`, чтобы существовать.

Ответ преподавателю одной фразой: *«static означает, что член принадлежит классу, а не экземпляру; к нему обращаются через имя класса, и он существует в одном экземпляре».*

### `final`

`final` = «нельзя изменить / переопределить». Смысл зависит от того, к чему применено:

| К чему | Значение | Пример в лабе |
|---|---|---|
| поле / переменная | значение присваивается **один раз** и больше не меняется | `private final Stage stage;`, `private final CsvErrorCode code;` |
| класс | от класса **нельзя наследоваться** | `public final class ClosedTicket`, `HomeVisitTicket`, `final class CsvFormat`, `Dialogs`, `TicketDialog`, `TicketTableFactory` |
| метод | метод **нельзя переопределить** в наследнике | в лабе не используется |

Важный нюанс: `final` на поле-ссылке запрещает **переприсвоить ссылку**, но не запрещает **менять сам объект**. Пример: `private final TicketHeap<Ticket> heap` — написать `heap = new TicketHeap<>(...)` нельзя, а `heap.insert(...)` можно.

### `static final` вместе

`public static final int MAX_URGENCY = 3;` — это **константа**: одна на класс (`static`) и неизменяемая (`final`). Константы по соглашению пишут `UPPER_SNAKE_CASE`.

### Остальные ключевые слова, которые встречаются в коде

| Слово | Что значит |
|---|---|
| `package app;` | в каком пакете (папке) лежит класс; должно совпадать с папкой |
| `import` | подключить класс из другого пакета, чтобы писать короткое имя |
| `class` | объявление класса — шаблона для объектов |
| `interface` | контракт: список методов, которые класс обязан реализовать (`Editable`, `Serializer`) |
| `abstract` | класс: объект создать нельзя (`Ticket`); метод: тела нет, наследник обязан реализовать (`type()`) |
| `enum` | тип с фиксированным набором значений (`CsvErrorCode`, `TicketType`) |
| `record` | короткий неизменяемый класс-«контейнер данных» (`LoadResult`, `TicketDto`, `Priority`), Java 16+ |
| `extends` | наследование от класса (`HomeVisitTicket extends RegularTicket`); у класса только один родитель |
| `implements` | реализация интерфейса (`RegularTicket implements Editable`); интерфейсов может быть много |
| `@Override` | аннотация «этот метод переопределяет метод родителя/интерфейса»; компилятор проверит, что такой метод действительно есть |
| `this` | ссылка на текущий объект; `this.address = address` — поле объекта = параметр |
| `super(...)` | вызов конструктора родителя (должен быть первой строкой конструктора) |
| `super.toString()` | вызов версии метода из родительского класса |
| `new` | создание объекта |
| `void` | метод ничего не возвращает |
| `return` | выйти из метода (и вернуть значение) |
| `null` | «ссылка ни на что» |
| `throw` | бросить исключение |
| `throws` | в сигнатуре: «метод может бросить это проверяемое исключение» |
| `try / catch` | перехват исключений |
| `try (...) { }` | try-with-resources: ресурс (файл) закроется автоматически |
| `instanceof` | проверка «объект является экземпляром типа?» |
| `x instanceof Foo f` | pattern matching (Java 16+): проверка + сразу приведение к типу в переменную `f` |
| `switch (x) { case A -> ...; }` | switch-выражение со стрелками (Java 14+): возвращает значение, без `break` |
| `continue` | перейти к следующей итерации цикла |
| `->` (лямбда) | анонимная функция: `event -> addTicket()` |
| `::` | ссылка на метод: `files::loadCsv` = `() -> files.loadCsv()` |
| `synchronized` | метод выполняется под монитором объекта: потоки входят по очереди (`SynchronizedTicketHeap`) |
| `<T>` (генерики) | параметр типа: `List<String>` — список именно строк, `TicketHeap<T>` — куча любых элементов |
| `<>` (diamond) | компилятор сам выводит тип: `new ArrayList<>()` |

### Проверяемые и непроверяемые исключения

- **Checked** (наследники `Exception`, но не `RuntimeException`) — компилятор **заставляет** либо поймать их `catch`, либо объявить `throws`. В лабе: `IOException`, свои `CsvLoadException` и `SerializationException`.
- **Unchecked** (наследники `RuntimeException`) — обрабатывать не обязательно. В лабе: `NumberFormatException`, `DateTimeParseException`, `IllegalArgumentException`, `NullPointerException`.

### Принципы ООП в лабе (часто спрашивают)

| Принцип | Где в коде |
|---|---|
| **Инкапсуляция** | поля закрыты, доступ через методы; массив `TicketHeap` не виден снаружи |
| **Наследование** | `RegularTicket` и `ClosedTicket` наследуют `Ticket`, `HomeVisitTicket` наследует `RegularTicket` |
| **Полиморфизм** | `ticket.type()` и `ticket.getAddress()` вызывают версию реального класса; `TicketHeap<Ticket>` хранит объекты всех трёх классов; `Serializer` работает для обоих форматов |
| **Абстракция** | интерфейсы `Editable` и `Serializer` описывают «что умеет», не «как»; абстрактный класс `Ticket` |

## 2. `pom.xml` — сборка проекта

Maven — система сборки. `pom.xml` (Project Object Model) описывает проект: имя, версию Java, зависимости, плагины.

```xml
<?xml version="1.0" encoding="UTF-8"?>
```
Заголовок XML-документа: версия XML и кодировка.

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
```
- `<project>` — корневой тег.
- `xmlns` — пространство имён POM.
- `xmlns:xsi` и `xsi:schemaLocation` — где лежит схема, по которой IDE проверяет правильность тегов.

```xml
<modelVersion>4.0.0</modelVersion>
```
Версия формата POM. Для Maven 2/3 всегда `4.0.0`.

```xml
<groupId>org.example</groupId>
<artifactId>proglab6</artifactId>
<version>1.0-SNAPSHOT</version>
```
«Координаты» проекта:
- `groupId` — организация/группа (обычно обратный домен);
- `artifactId` — имя проекта;
- `version` — версия; `SNAPSHOT` означает «рабочая, ещё не выпущенная».

```xml
<properties>
    <maven.compiler.release>25</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <javafx.version>25.0.2</javafx.version>
    <jackson.version>2.22.4</jackson.version>
    <junit.version>5.13.4</junit.version>
</properties>
```
- `maven.compiler.release` = 25 — компилировать под Java 25 (и проверять, что используется только API Java 25).
- `project.build.sourceEncoding` = UTF-8 — кодировка исходников (важно из-за русских строк).
- `javafx.version`, `jackson.version`, `junit.version` — **свои** переменные, чтобы версию указать в одном месте.

```xml
<dependencies>
    <dependency>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-controls</artifactId>
        <version>${javafx.version}</version>
    </dependency>
</dependencies>
```
Зависимость — библиотека, которую Maven скачает сам. `javafx-controls` содержит кнопки, таблицы, диалоги (и тянет за собой `javafx-base`, `javafx-graphics`). `${javafx.version}` — подстановка значения из `<properties>`.

Для ЛР3 добавлены ещё три зависимости:

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>${jackson.version}</version>
</dependency>
<dependency>
    <groupId>com.fasterxml.jackson.datatype</groupId>
    <artifactId>jackson-datatype-jsr310</artifactId>
    <version>${jackson.version}</version>
</dependency>
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>${junit.version}</version>
    <scope>test</scope>
</dependency>
```
- `jackson-databind` — чтение и запись JSON;
- `jackson-datatype-jsr310` — поддержка `LocalDateTime`;
- `junit-jupiter` — JUnit 5. `<scope>test</scope>` значит, что библиотека нужна только для тестов и не попадает в программу.

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.14.1</version>
        </plugin>
```
Плагин, который компилирует `.java` в `.class`. Версия явно указана, чтобы сборка была воспроизводимой.

```xml
        <plugin>
            <groupId>org.openjfx</groupId>
            <artifactId>javafx-maven-plugin</artifactId>
            <version>0.0.8</version>
            <configuration>
                <mainClass>app.Main</mainClass>
            </configuration>
        </plugin>
```
Плагин для запуска JavaFX-приложения командой `mvn javafx:run`. `mainClass` — полное имя класса с методом `main` (пакет `app`, класс `Main`).

Ещё два плагина: `maven-surefire-plugin` запускает тесты при `mvn test`, `exec-maven-plugin` запускает замеры (`HeapBenchmark`, `FormatComparison`), см. раздел 11.

## 3. `.gitignore`

Список файлов, которые Git **не должен** добавлять в репозиторий:
- `/target/` — результат сборки Maven (скомпилированные классы);
- `/.idea/`, `*.iml`, `*.iws`, `*.ipr`, `/out/` — служебные файлы IntelliJ IDEA;

- `*.tmp`, `*.swp`, `*~` — временные файлы редакторов;
- `.DS_Store`, `._*` — служебные файлы macOS.

## 4. Пакет `app` — запуск

### 4.1 `Main.java`

```java
package app;

public class Main {
    public static void main(String[] args) {
        ClinicApplication.launchApplication(args);
    }
}
```

| Фрагмент | Объяснение |
|---|---|
| `package app;` | класс лежит в пакете `app` (папка `app/`) |
| `public class Main` | публичный класс; имя файла обязано совпадать: `Main.java` |
| `public` (у `main`) | JVM должна иметь доступ к методу извне |
| `static` | JVM вызывает `main` без создания объекта `Main` |
| `void` | ничего не возвращает |
| `String[] args` | аргументы командной строки (массив строк) |
| `ClinicApplication.launchApplication(args)` | вызов **статического** метода другого класса; передаём аргументы дальше |

**Зачем отдельный `Main`, если есть `ClinicApplication`?** Если класс с `main` сам наследует `javafx.application.Application`, то Java при запуске без модулей выдаёт ошибку *«JavaFX runtime components are missing»*. Отдельный класс-«пускач», который **не** наследует `Application`, обходит эту проверку. Это стандартный приём.

### 4.2 `ClinicApplication.java`

```java
package app;

import controller.MainController;
import javafx.application.Application;
import javafx.scene.Scene;
import javafx.stage.Stage;
```
Импорты: наш контроллер и классы JavaFX:
- `Application` — базовый класс любого JavaFX-приложения;
- `Stage` — окно;
- `Scene` — «содержимое» окна (дерево элементов).

Аналогия: `Stage` — сцена театра (рамка окна), `Scene` — декорации на ней.

```java
public class ClinicApplication extends Application {
```
`extends Application` — наследуемся от `Application`, чтобы JavaFX мог управлять жизненным циклом приложения (`init` → `start` → `stop`).

```java
    @Override
    public void start(Stage stage) {
```
- `start` — **абстрактный** метод `Application`, его обязательно надо переопределить.
- JavaFX сам вызывает его в специальном потоке интерфейса (JavaFX Application Thread) и передаёт уже созданное главное окно `stage`.
- `@Override` — гарантия, что мы действительно переопределяем метод (опечатку в имени компилятор поймает).

```java
        MainController controller = new MainController(stage);
```
Создаём контроллер, передаём ему окно (оно нужно для диалогов выбора файла и сообщений об ошибках).

```java
        Scene scene = new Scene(controller.createView(), WINDOW_WIDTH, WINDOW_HEIGHT);
```
`controller.createView()` строит интерфейс и возвращает корневой элемент (`Parent`). Сцена создаётся с этим корнем и размером 1200×800 пикселей: окну нужно место для таблицы и дерева кучи.

```java
        stage.setTitle(MainController.TITLE);
        stage.setMinWidth(MIN_WIDTH);
        stage.setMinHeight(MIN_HEIGHT);
        stage.setScene(scene);
        stage.show();
    }
```
- `setTitle` — заголовок окна;
- `setMinWidth/Height` — окно нельзя сжать меньше этих размеров;
- `setScene` — кладём сцену в окно;
- `show()` — показать окно.

```java
    public static void launchApplication(String[] args) {
        launch(args);
    }
}
```
- `launch(args)` — **статический** метод `Application`: запускает JavaFX-рантайм, создаёт объект `ClinicApplication`, вызывает `start(...)`. Метод блокирует поток, пока окно не закроют.
- `launch` без указания класса определяет «какое приложение запускать» по классу, из которого его вызвали — поэтому вызов обёрнут в метод внутри `ClinicApplication`.
- `static` — чтобы `Main` мог вызвать его, не создавая объект.

## 5. Пакет `model` — данные (талоны)

### 5.1 `Editable.java` — интерфейс

```java
package model;

import java.util.List;

public interface Editable {
	List<String> validate();
}
```
- `interface` — контракт: «класс, реализующий `Editable`, обязан иметь метод `validate()`».
- Методы интерфейса по умолчанию `public abstract` — писать эти слова не нужно.
- `List<String> validate()` — проверяет данные и возвращает **список текстов ошибок**. Пустой список = ошибок нет.
- Смысл названия: «объект можно менять, и он умеет проверить свои данные».

**Почему интерфейс с методом, а не маркер без методов?** Кто разрешает изменение, тот должен уметь проверить результат. С маркером проверку пришлось бы держать снаружи и ветвить по типам. С методом диалог работает с обычным талоном и талоном на дому одинаково, а талон на дому добавляет проверку адреса переопределением.

Интерфейс реализует `RegularTicket`, а `HomeVisitTicket` получает его по наследству. `ClosedTicket` интерфейс не реализует, поэтому кнопка «Изменить» проверяет только `instanceof Editable`.

### 5.2 `Ticket.java` — абстрактный базовый класс

```java
package model;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
```
- `LocalDateTime` — дата + время без часового пояса (например, `2026-09-24T10:30`).
- `ArrayList` — реализация списка на массиве; `List` — интерфейс списка.
- `Comparator` — объект, который умеет сравнивать два значения.

```java
public abstract class Ticket {
```
`abstract` — создать объект этого класса нельзя, `new Ticket(...)` не скомпилируется. Талон всегда обычный, на дому или закрытый. Здесь лежит только общее: поля, геттеры, проверка общих полей. `Editable` этот класс **не** реализует, и в этом смысл исправления ЛР1: раньше закрытый талон формально был редактируемым.

```java
    public static final int MIN_URGENCY = 0;
    public static final int MAX_URGENCY = 3;
```
Границы срочности: константы вместо «магических чисел» 0 и 3. Их используют проверка, диалог и генератор.

```java
    // Порядок в очереди: сначала меньшая срочность, при равенстве раньше взятый талон
    public static final Comparator<Ticket> PRIORITY =
            Comparator.comparingInt(Ticket::getUrgency).thenComparing(Ticket::getTakenAt);
```
Компаратор варианта 6, его получает куча.
- `Comparator.comparingInt(Ticket::getUrgency)` — сравнивать по числу, которое вернёт геттер. Меньше = важнее, поэтому срочность 0 окажется в корне кучи, как в примере из задания.
- `.thenComparing(Ticket::getTakenAt)` — если срочность равна, сравнить время. `LocalDateTime` умеет сравниваться сам.

```java
    protected String cardNumber;
    protected String fullName;
    protected String room;
    protected int urgency;
    protected LocalDateTime takenAt;
```
Поля объекта (у каждого талона свои):
- `cardNumber` — номер медкарты;
- `fullName` — ФИО;
- `room` — кабинет (строка, т.к. бывает «12а»);
- `urgency` — срочность 0–3; `int` — примитивный тип, не может быть `null`, по умолчанию 0;
- `takenAt` — когда взят талон.

`protected` — поле видно наследникам: сеттеры `RegularTicket` пишут в него напрямую. Снаружи пакета `model` и вне наследников поле не доступно. Не `final`, потому что обычный талон меняется.

```java
    protected Ticket(String cardNumber, String fullName, String room, int urgency, LocalDateTime takenAt) {
        this.cardNumber = cardNumber;
        this.fullName = fullName;
        this.room = room;
        this.urgency = urgency;
        this.takenAt = takenAt;
    }
```
**Конструктор** вызывают только наследники через `super(...)`, поэтому он `protected`. Имя = имя класса, без возвращаемого типа.
`this.cardNumber = cardNumber;` — параметр называется так же, как поле, поэтому `this.` указывает: «слева — поле объекта, справа — параметр».

```java
    public abstract TicketType type();
```
Абстрактный метод: тела нет, каждый наследник обязан его реализовать. Так каждый класс сам сообщает свой тип, а загрузчикам и сохранителям не нужны цепочки `instanceof`.

```java
    public String getCardNumber() {
        return cardNumber;
    }
```
- `public` — доступен из любого класса (таблица, CSV-сохранитель);
- `String` — тип возвращаемого значения совпадает с типом поля;
- `getCardNumber` — имя по соглашению JavaBeans: `get` + имя поля с большой буквы;
- `()` — параметров нет;
- `return cardNumber;` — вернуть значение поля (`this.` можно не писать: конфликта имён нет).

Геттеры `getFullName`, `getRoom`, `getUrgency`, `getTakenAt` устроены так же. `LocalDateTime` — неизменяемый (immutable) класс, поэтому отдавать ссылку на него наружу безопасно. Сеттеров в этом классе нет.

```java
    public String getAddress() {
        return "";
    }
```
Адрес есть только у `HomeVisitTicket`, он переопределяет этот метод. Пустая строка в базовом классе убирает проверки `instanceof` из таблицы, CSV и сериализаторов: они просто вызывают `getAddress()` у любого талона. Это полиморфизм.

```java
    public List<String> validateCommon() {
        List<String> errors = new ArrayList<>();
```
Проверка общих для всех талонов полей. Она в базовом классе, потому что нужна всем, в том числе закрытому талону при чтении из файла.
`List<String> errors = new ArrayList<>();` — тип переменной — интерфейс `List`, объект — `ArrayList`; `<>` — тип выводится сам (`String`).

```java
        validateRequired("Номер карты", cardNumber, errors);
        validateRequired("ФИО", fullName, errors);
        validateRequired("Кабинет", room, errors);
```
Три обязательных строковых поля проверяются одним вспомогательным методом (нет дублирования кода).

```java
        if (urgency < MIN_URGENCY || urgency > MAX_URGENCY) {
            errors.add("Срочность должна быть от " + MIN_URGENCY + " до " + MAX_URGENCY);
        }
```
`||` — логическое «ИЛИ» (с коротким замыканием: если первое условие истинно, второе не проверяется).

```java
        if (takenAt == null) {
            errors.add("Время взятия не указано");
        }
        return errors;
    }
```
`== null` — проверка, что ссылка пустая. Возвращаем список всех найденных ошибок (а не только первую).

```java
    private void validateRequired(String field, String value, List<String> errors) {
        if (value == null || value.isBlank()) {
            errors.add(field + " не может быть пустым");
            return;
        }
        if (value.contains(";")) {
            errors.add(field + " не может содержать ';'");
        }
    }
```
- `private` — вспомогательный, снаружи не нужен.
- `value == null || value.isBlank()` — порядок важен: сначала проверка на `null`, иначе `value.isBlank()` на `null` бросит `NullPointerException`. `isBlank()` (Java 11+) — строка пустая или только из пробелов.
- `return;` — досрочный выход из `void`-метода: если пусто, дальше проверять нечего.
- `contains(";")` — запрет `;`, потому что это **разделитель в CSV**: если он окажется внутри значения, файл «поедет».

Список `errors` передаётся **по ссылке**, поэтому метод добавляет ошибки прямо в список вызывающего.

```java
    @Override
    public String toString() {
        return cardNumber + ", " + fullName + ", каб. " + room
                + ", срочность: " + urgency + ", " + takenAt;
    }
}
```
Переопределение `Object.toString()` — текстовое представление объекта (используется в статусе, Top-K и отладке). `+` для строк — конкатенация.

### 5.3 `RegularTicket.java` — обычный талон

**Что делает.** Первый редактируемый класс иерархии: добавляет к базовому классу сеттеры, `validate()` и `copyFrom`.

```java
public class RegularTicket extends Ticket implements Editable {
```
- `extends Ticket` — получает поля и геттеры.
- `implements Editable` — обычный талон можно редактировать.

```java
    public RegularTicket(String cardNumber, String fullName, String room, int urgency, LocalDateTime takenAt) {
        super(cardNumber, fullName, room, urgency, takenAt);
    }
```
Конструктор передаёт всё родителю. `super(...)` обязан быть первой строкой.

```java
    @Override
    public TicketType type() {
        return TicketType.TICKET;
    }
```
Реализация абстрактного метода родителя.

```java
    public void setCardNumber(String cardNumber) {
        this.cardNumber = cardNumber;
    }
```
- `void` — ничего не возвращает;
- `setCardNumber` — `set` + имя поля;
- `this.cardNumber = cardNumber;` — поле объекта (`this.`) получает значение параметра. Без `this.` параметр присвоился бы сам себе, и поле не изменилось бы.

Сеттеры `setFullName`, `setRoom`, `setUrgency`, `setTakenAt` устроены так же. Сеттер **не проверяет** диапазон срочности: проверка вынесена в `validate()`.

**Важно про кучу:** срочность и время влияют на положение талона. Если вызвать `setUrgency` у талона из очереди напрямую, куча перестанет быть кучей. Поэтому в `src/main` сеттеры приоритета вызываются только внутри `changePriority` (см. `MainController.updateInHeap`).

```java
    public void copyFrom(RegularTicket source) {
        cardNumber = source.cardNumber;
        fullName = source.fullName;
        room = source.room;
        urgency = source.urgency;
        takenAt = source.takenAt;
    }
```
Копирует значения из объекта, который вернул диалог. Раньше это делал контроллер, теперь список полей знает только модель.

```java
    @Override
    public List<String> validate() {
        return validateCommon();
    }
}
```
Реализация метода интерфейса `Editable`: обычный талон проверяет только общие поля.

**Вопросы преподавателя**

**Почему сеттеры здесь, а не в `Ticket`?**
Иначе они достались бы и `ClosedTicket`, и пришлось бы снова бросать исключения. Теперь у закрытого талона сеттеров просто нет.

**Зачем `copyFrom`, если есть сеттеры?**
Контроллеру не нужно знать список полей. Талон на дому переопределяет метод и добавляет адрес.

### 5.4 `HomeVisitTicket.java` — вызов на дом

```java
public final class HomeVisitTicket extends RegularTicket {
```
`extends RegularTicket` — талон на дому является обычным талоном с адресом: наследует сеттеры, `copyFrom` и `Editable`. Дублировать пять сеттеров не нужно.

```java
    private String address;

    public HomeVisitTicket(String cardNumber, String fullName, String room, int urgency,
                           LocalDateTime takenAt, String address) {
        super(cardNumber, fullName, room, urgency, takenAt);
        this.address = address;
    }
```
Дополнительное поле — адрес. `super(...)` вызывает конструктор `RegularTicket`, затем инициализируем своё поле.

```java
    @Override
    public TicketType type() {
        return TicketType.HOME;
    }

    @Override
    public String getAddress() {
        return address;
    }

    public void setAddress(String address) {
        this.address = address;
    }
```
Свой тип, переопределённый геттер адреса и сеттер.

```java
    @Override
    public void copyFrom(RegularTicket source) {
        super.copyFrom(source);
        if (source instanceof HomeVisitTicket home) {
            address = home.address;
        }
    }
```
`super.copyFrom(source)` копирует общие поля, затем копируем адрес. Это переопределение, а не перегрузка: параметр имеет тип `RegularTicket`. Если бы был метод `copyFrom(HomeVisitTicket)`, компилятор выбирал бы его по типу переменной, и вызов через `RegularTicket` молча терял бы адрес.

```java
    @Override
    public List<String> validate() {
        List<String> errors = new ArrayList<>(validateCommon());
```
Переопределяем проверку. `new ArrayList<>(validateCommon())` — создаём новый список, **скопировав** в него ошибки общих полей (конструктор-копия).

```java
        if (address == null || address.isBlank()) {
            errors.add("Не указан адрес");
        } else if (address.contains(";")) {
            errors.add("Поля не должны содержать символ ';'");
        }
        return errors;

```
Добавляем проверку адреса. Это **полиморфизм**: вызов `ticket.validate()` для объекта `HomeVisitTicket` выполнит именно эту версию, даже если переменная имеет тип `RegularTicket`.

```java
    @Override
    public String toString() {
        return super.toString() + ", адрес: " + address;
    }
}
```
`super.toString()` — берём строку родителя и дописываем адрес (не дублируем код).

### 5.5 `ClosedTicket.java` — закрытый талон (только чтение)

```java
public final class ClosedTicket extends Ticket {

    public ClosedTicket(String cardNumber, String fullName, String room, int urgency, LocalDateTime takenAt) {
        super(cardNumber, fullName, room, urgency, takenAt);
    }

    @Override
    public TicketType type() {
        return TicketType.CLOSED;
    }
}
```
Весь класс. В этом и смысл: сеттеров нет, `Editable` нет.
- `extends Ticket`, а не `RegularTicket`: закрытый талон не является редактируемым.
- `final class` — от него нельзя наследоваться, поэтому никто не добавит сеттеры в подклассе.
- Попытка изменить закрытый талон — **ошибка компиляции**, а не исключение во время работы.

Как создаётся закрытый талон: в диалоге такого типа нет, генератор его не создаёт — только чтением из файла (тип `CLOSED`), как и требует задание.

**Вопросы преподавателя**

**Как проверяется, что закрытый талон нельзя изменить?**
Компилятором: у него нет сеттеров. Кнопки «Изменить» и «Изменить приоритет» отключены проверкой `instanceof Editable`, а тест `closedTicketIsNotEditable` фиксирует, что он не реализует интерфейс.

**Что было неправильно в ЛР1?**
`Ticket implements Editable` и `ClosedTicket extends Ticket`: закрытый талон формально был `Editable`. Отсюда проверки `instanceof ClosedTicket` и сеттеры с исключением, которые нарушали принцип подстановки Лисков.

### 5.6 `TicketType.java` — тип талона

**Что делает.** Перечисление типов и единая точка создания талона при чтении файлов. Его используют CSV, bin и JSON.

```java
public enum TicketType {
    TICKET(1),
    HOME(2),
    CLOSED(3);

    // Код записывается в бинарный файл, поэтому не зависит от порядка констант
    private final int code;

    TicketType(int code) {
        this.code = code;
    }

    public int code() {
        return code;
    }
```
`enum` может иметь поля и конструктор. Имена констант совпадают со значениями в CSV и JSON. Число `code` пишется в бинарный файл. `ordinal()` для этого не подходит: если поменять константы местами, старые файлы станут читаться неверно.

```java
    public static Optional<TicketType> parse(String name) {
        for (TicketType type : values()) {
            if (type.name().equals(name)) {
                return Optional.of(type);
            }
        }
        return Optional.empty();
    }
```
Поиск типа по имени. `values()` — все константы enum. `Optional` вместо исключения: неизвестный тип здесь обычная ситуация, вызывающий сам решает, какую ошибку выдать. `fromCode` устроен так же, но ищет по числу.

```java
    // Единая точка создания талона при чтении файлов любого формата.
    // Некорректные данные дают IllegalArgumentException, вызывающий код переводит его в свою ошибку
    public Ticket create(String cardNumber, String fullName, String room, int urgency,
                         LocalDateTime takenAt, String address) {
        Ticket ticket = switch (this) {
            case TICKET -> new RegularTicket(cardNumber, fullName, room, urgency, takenAt);
            case HOME -> new HomeVisitTicket(cardNumber, fullName, room, urgency, takenAt, address);
            case CLOSED -> new ClosedTicket(cardNumber, fullName, room, urgency, takenAt);
        };
```
`switch` по `this` — по самой константе. `default` не нужен: компилятор знает, что значений enum только три, и проверяет, что все перечислены.

```java
        List<String> errors = ticket instanceof Editable editable
                ? editable.validate()
                : ticket.validateCommon();
        if (!errors.isEmpty()) {
            throw new IllegalArgumentException(String.join("; ", errors));
        }
        return ticket;
    }
}
```
Редактируемый талон проверяет себя сам, закрытый проверяется по общим полям. Модель не знает про `CsvLoadException` и `SerializationException`, поэтому бросает стандартное исключение, а `CsvLoader` и сериализаторы переводят его в свою ошибку.

**Вопросы преподавателя**

**Зачем enum, если были константы `CSV_TYPE`?**
Константы были строками в трёх классах, а `CsvSaver` определял тип цепочкой `instanceof`. Теперь `ticket.type()` работает для любого талона, а набор типов проверяет компилятор.

## 6. Пакет `csv` — чтение и запись файла

Формат файла (пример):
```
type;cardNumber;fullName;room;urgency;takenAt;address
TICKET;A-101;Иванов Иван Иванович;12;1;2026-09-24T10:30;
HOME;A-102;Петров Пётр;—;3;2026-09-24T11:00;ул. Ленина, 5
CLOSED;A-103;Сидорова Анна;7;0;2026-09-23T09:15;
```
Всегда 7 колонок; у не-домашних талонов адрес — пустая строка.

### 6.1 `CsvFormat.java` — константы формата

```java
public final class CsvFormat {
    public static final String DELIMITER = ";";
    public static final int COLUMN_COUNT = 7;
    public static final String HEADER = "type;cardNumber;fullName;room;urgency;takenAt;address";
    private CsvFormat() { }
}
```
- **Утилитный класс констант**: всё, что касается формата, лежит в одном месте; загрузчик и сохранитель гарантированно используют одинаковые значения.
- `final class` — наследоваться не нужно.
- `private CsvFormat() { }` — **приватный конструктор**: запрещает `new CsvFormat()`. Объект этого класса бессмысленен, всё в нём `static`.


### 6.2 `CsvErrorCode.java` — коды ошибок

```java
public enum CsvErrorCode {
    BAD_NUMBER,
    WRONG_FIELD_COUNT,
    BAD_DATE,
    UNKNOWN_TYPE,
    INVALID_DATA
}
```
- `enum` — перечисление: тип, у которого есть только эти значения. Каждое значение — объект-константа (`public static final` неявно).
- `BAD_NUMBER` — срочность не число, `WRONG_FIELD_COUNT` — не 7 колонок, `BAD_DATE` — дата в неверном формате, `UNKNOWN_TYPE` — тип не TICKET/HOME/CLOSED, `INVALID_DATA` — не прошла проверка полей.
- Лучше «магических строк»: опечатку `BAD_NUBMER` поймает компилятор.
- При выводе в строку значение печатается своим именем (`[BAD_DATE]`).

### 6.3 `CsvLoadException.java` — своё исключение

```java
public class CsvLoadException extends Exception {
    private final CsvErrorCode code;

    public CsvLoadException(CsvErrorCode code, String message) {
        super(message);
        this.code = code;
    }
    public CsvErrorCode getCode() { return code; }
}
```
- `extends Exception` — **проверяемое (checked)** исключение: компилятор заставит обработать его или объявить `throws`. Так ошибку разбора строки нельзя «забыть».
- `private final CsvErrorCode code` — код ошибки; `final` — задаётся один раз в конструкторе и не меняется.
- `super(message)` — передаём текст в конструктор `Exception`; потом он доступен через `getMessage()`.
- `getCode()` — вернуть код.


### 6.4 `CsvLoader.java` — загрузка

```java
import java.io.IOException;               // ошибка ввода-вывода

```

```java
public class CsvLoader {
    private static final char BOM = '\uFEFF';
```

**Где хранятся данные: в таблице или в куче?**

### 7.5 `HeapCanvas.java` — панель кучи

**Что делает.** Рисует дерево по индексам массива и строку самого массива, подсвечивает узлы, посещённые последней операцией.

```java
public class HeapCanvas extends Pane {
    private static final int MAX_LEVELS = 6;
    private static final int MAX_NODES = (1 << MAX_LEVELS) - 1;
```
`1 << 6` — сдвиг, это 2⁶ = 64. Шесть уровней дают 63 узла: больше на экране не поместится.

```java
    private final TicketHeap<Ticket> heap;
    private final Canvas canvas = new Canvas();

    public HeapCanvas(TicketHeap<Ticket> heap) {
        this.heap = heap;
        getChildren().add(canvas);
        setMinSize(0, 0);
        canvas.widthProperty().bind(widthProperty());
        canvas.heightProperty().bind(heightProperty());
        widthProperty().addListener(observable -> redraw());
        heightProperty().addListener(observable -> redraw());
    }
```
`Canvas` — холст, на котором рисуют командами. Сам он размер не меняет, поэтому лежит внутри `Pane`, а его ширина и высота привязаны к размерам панели. При изменении размера картинка рисуется заново.

```java
    public void redraw() {
        double width = getWidth();
        double height = getHeight();
        GraphicsContext g = canvas.getGraphicsContext2D();
        g.setFill(BACKGROUND);
        g.fillRect(0, 0, width, height);
        g.setTextBaseline(VPos.CENTER);
```
**Полная перерисовка**: сначала закрашиваем всё фоном. `GraphicsContext` — объект с командами рисования.

```java

        int shownCells = Math.min(size, (int) ((width - 2 * MARGIN) / CELL_WIDTH));
        int[] visited = heap.lastVisited();
        boolean[] highlighted = highlightedNodes(visited, Math.max(shownNodes, shownCells));
        int last = visited.length == 0 ? -1 : visited[visited.length - 1];
```
Количество элементов на экране ограничено, поэтому отрисовка стоит одинаково и на 30, и на миллионе талонов. `highlighted[i]` — посещён ли узел i, `last` — последний посещённый, он выделяется оранжевым.

```java
    private static int levelOf(int index) {
        int level = 0;
        while (index >= (1 << (level + 1)) - 1) {
            level++;
        }
        return level;
    }

    private static double nodeX(int index, double width) {
        int level = levelOf(index);
        int positionInLevel = index + 1 - (1 << level);
        return (positionInLevel + 0.5) * width / (1 << level);
    }
```
Положение узла полностью следует из индекса. На уровне L лежит 2^L узлов, начиная с индекса 2^L − 1. Ширина делится на 2^L равных частей, узел стоит в середине своей части. Так дерево строится по индексам массива без отдельных объектов-узлов.

```java
        g.setStroke(EDGE);
        for (int i = 1; i < nodes; i++) {
            int parent = (i - 1) / 2;
            g.strokeLine(nodeX(parent, width), nodeY(parent, levelHeight), nodeX(i, width), nodeY(i, levelHeight));
        }
```
Рёбра рисуются первыми, чтобы круги легли поверх них. Родитель считается той же формулой, что и в куче.

```java
    private Color colorOf(int index, boolean[] highlighted, int last) {
        if (index == last) {
            return LAST_VISITED;
        }
        return highlighted[index] ? VISITED : NODE;
    }
```
Один метод выбирает цвет и для круга, и для ячейки массива, поэтому дерево и строка подсвечиваются одинаково.

**Вопросы преподавателя**

**Что будет при 10⁶ элементов?**
Рисуются первые 6 уровней и столько ячеек, сколько помещается, подпись сообщает «Показано X из N». Время отрисовки не зависит от размера очереди.

**Почему `Canvas`, а не `Circle` и `Line`?**
Так рекомендует задание: полная перерисовка простыми командами, не нужно хранить и обновлять объекты узлов.

**Вопросы преподавателя**

**Почему нельзя просто читать файл в обработчике кнопки?**
Обработчик выполняется в FX-потоке, который рисует окно. Пока он занят, окно не реагирует. По заданию блокировка дольше 100 мс снижает оценку.

**Что делает `cancel()`?**
Ставит задаче состояние CANCELLED и прерывает поток. Код в `call()` при этом не останавливается сам, он должен проверять `isCancelled()`. После отмены `onSucceeded` не вызывается, поэтому результат отменённой задачи никуда не попадёт.

**Что делает.** Создаёт объекты `Task`. Правило одно: задача работает только с локальными данными и не трогает основную кучу. Готовый результат подменяет FX-поток, когда задача завершилась.

## 8. Пакет `structure` — куча

### 8.1 `TicketHeap.java` — двоичная min-куча

**Что делает.** Хранит элементы в массиве так, что минимум всегда в ячейке 0. Для узла i родитель находится в `(i-1)/2`, дети в `2i+1` и `2i+2`. Инвариант: приоритет родителя не больше приоритетов детей. Порядка между братьями нет, поэтому куча не отсортирована.

```
массив: [ 1 │ 3 │ 2 │ 5 │ 4 │ 3 │ 6 ]
индекс:   0   1   2   3   4   5   6

дерево:        1
             /   \
            3     2
           / \   / \
          5   4 3   6
```

**Как работает.**

```java
public class TicketHeap<T> {
    private static final int INITIAL_CAPACITY = 16;
    private static final int GROWTH_FACTOR = 2;

    private final Comparator<T> comparator;
    private T[] items;
    private int size;
```
- `<T>` — тип элемента. Куча ничего не знает про талоны: `TicketHeap<Ticket>` в очереди, `TicketHeap<Integer>` в демонстрации гонки и в `topK`.
- `comparator` задаёт порядок, он приходит в конструкторе.
- `items` — массив, `size` — сколько ячеек реально занято. Ёмкость массива больше или равна `size`.

```java
    // Индексы узлов, посещённых последней операцией, в порядке обхода
    private int[] visited = new int[INITIAL_CAPACITY];
    private int visitedCount;
```
Путь для подсветки. Это обычный массив `int`, а не `List<Integer>`: дешевле и не нужны готовые коллекции.

```java
    public TicketHeap(Comparator<T> comparator) {
        this.comparator = comparator;
        this.items = newArray();
    }

    @SuppressWarnings("unchecked") // Массив T[] создать нельзя, но наружу он не выходит
    private T[] newArray() {
        return (T[]) new Object[INITIAL_CAPACITY];
    }
```
Java не разрешает `new T[...]`: при выполнении тип `T` стёрт. Поэтому создаётся `Object[]` и приводится к `T[]`. Компилятор предупреждает, аннотация это предупреждение убирает. Это безопасно, потому что массив не выходит за пределы класса.

```java
    public void insert(T item) {
        Objects.requireNonNull(item, "item");
        startVisit();
        ensureCapacity(size + 1);
        items[size] = item;
        size++;
        siftUp(size - 1);
    }
```
**Вставка.** Кладём в первую свободную ячейку, затем элемент всплывает. `requireNonNull` стоит первым: иначе `size` увеличился бы, а сравнение с `null` упало бы, и куча осталась бы испорченной.

```java
    private int siftUp(int index) {
        visit(index);
        while (index > 0 && comparator.compare(items[index], items[parent(index)]) < 0) {
            swap(index, parent(index));
            index = parent(index);
            visit(index);
        }
        return index;
    }
```
**Всплытие.** Пока элемент меньше родителя, меняем их местами. `compare` возвращает отрицательное число, если первый меньше. Цикл идёт вверх, путь не длиннее высоты дерева, поэтому O(log n). Возвращает итоговый индекс.

```java
    public T peek() {
        requireNotEmpty();
        startVisit();
        visit(0);
        return items[0];
    }

    public T extractMin() {
        requireNotEmpty();
        return delete(0);
    }
```
`peek` смотрит минимум, `extractMin` извлекает: это удаление из ячейки 0.

```java
    // Возвращает индекс первого подходящего элемента или -1. Порядка по ключу поиска в куче нет, поэтому обход линейный
    public int find(Predicate<T> condition) {
        startVisit();
        for (int i = 0; i < size; i++) {
            visit(i);
            if (condition.test(items[i])) {
                return i;
            }
        }
        return -1;
    }
```
**Поиск.** Условие передаётся лямбдой, поэтому класс не знает про номер карты. Куча упорядочена по приоритету, а не по карте, поэтому обход всех элементов, O(n).

```java
    public T delete(int index) {
        checkIndex(index);
        startVisit();
        visit(index);
        T removed = items[index];
        int last = size - 1;
        items[index] = items[last];
        items[last] = null;
        size--;
        if (index < size) {
            restore(index);
        }
        return removed;
    }
```
**Удаление по индексу.** На место удаляемого ставим последний элемент, ячейку обнуляем, чтобы объект мог собрать сборщик мусора. Если удаляли сам последний элемент, просеивать нечего, это условие `index < size`.

```java
    // Элемент мог стать и меньше родителя, и больше детей. Двигаем только в одну сторону
    private void restore(int index) {
        if (siftUp(index) == index) {
            siftDown(index);
        }
    }
```
После обмена с последним элемент может нарушить порядок в любую сторону. Если всплыть не удалось, пробуем погрузить. Этот же метод использует `changePriority`.

```java
    private void siftDown(int index) {
        visit(index);
        while (left(index) < size) {
            int smallest = left(index);
            if (right(index) < size && comparator.compare(items[right(index)], items[smallest]) < 0) {
                smallest = right(index);
            }
            if (comparator.compare(items[smallest], items[index]) >= 0) {
                return;
            }
            swap(index, smallest);
            index = smallest;
            visit(index);
        }
    }
```
**Погружение.** Пока есть левый ребёнок, выбираем меньшего из детей. Если он не меньше элемента, порядок восстановлен. Иначе меняем местами и идём вниз. Меняться надо именно с меньшим ребёнком, иначе родителем станет больший из детей, и инвариант сломается.

```java
    // K самых приоритетных элементов по порядку, сама куча не меняется.
    // Минимум всегда лежит среди кандидатов: это корень и дети уже выбранных узлов
    public List<T> topK(int k) {
        startVisit();
        List<T> result = new ArrayList<>();
        if (size == 0 || k <= 0) {
            return result;
        }

        TicketHeap<Integer> candidates = new TicketHeap<>((a, b) -> comparator.compare(items[a], items[b]));
        candidates.insert(0);
```
**Top-K.** Вспомогательная куча хранит **индексы** кандидатов, сравнивая элементы, на которые они указывают. Сначала единственный кандидат — корень.

```java
        while (result.size() < k && !candidates.isEmpty()) {
            int index = candidates.extractMin();
            visit(index);
            result.add(items[index]);
            if (left(index) < size) {
                candidates.insert(left(index));
            }
            if (right(index) < size) {
                candidates.insert(right(index));
            }
        }
        return result;
    }
```
Берём лучшего кандидата, его дети становятся новыми кандидатами. Ребёнок не меньше родителя, поэтому следующий минимум точно среди кандидатов. За шаг уходит один и добавляются максимум два, поэтому кандидатов не больше k+1, а весь алгоритм стоит O(k log k) и не зависит от n. Основная куча только читается.

```java
    // Единственный безопасный способ изменить поля, влияющие на порядок: после change инвариант восстанавливается
    public void changePriority(int index, Consumer<T> change) {
        checkIndex(index);
        startVisit();
        visit(index);
        change.accept(items[index]);
        restore(index);
    }
```
**Изменение приоритета.** Само изменение передаётся лямбдой и выполняется внутри операции, поэтому забыть восстановить кучу невозможно.

```java
    // Склейка массивов и heapify за O(n + m). Вторая очередь не меняется
    public void merge(TicketHeap<T> other) {
        if (other == this) {
            throw new IllegalArgumentException("Нельзя слить очередь саму с собой");
        }
        startVisit();
        ensureCapacity(size + other.size);
        System.arraycopy(other.items, 0, items, size, other.size);
        size += other.size;
        heapify();
    }
```
**Слияние.** Копируем второй массив в конец первого, затем одним проходом восстанавливаем кучу. Слияние с самим собой запрещено: в куче оказались бы две ссылки на один изменяемый объект.

```java
    private void heapify() {
        for (int i = size / 2 - 1; i >= 0; i--) {
            siftDown(i);
        }
    }
```
**Heapify.** Листья уже являются кучами из одного элемента, поэтому начинаем с последнего родителя и идём к корню. Почему O(n), а не O(n log n): половина узлов это листья и не двигается, четверть опускается на 1 уровень, восьмая на 2 и так далее. Сумма n/4·1 + n/8·2 + n/16·3 + … меньше n.

```java
    // Забирает содержимое другой кучи за O(1): собрать её можно в фоне, а здесь только подменить массив.
    // Вторая куча остаётся пустой, иначе обе делили бы один массив
    public void replaceWith(TicketHeap<T> other) {
        if (other == this) {
            throw new IllegalArgumentException("Нельзя заменить очередь ей самой");
        }
        items = other.items;
        size = other.size;
        visited = other.visited;
        visitedCount = other.visitedCount;

        other.items = other.newArray();
        other.size = 0;
        other.visited = new int[INITIAL_CAPACITY];
        other.visitedCount = 0;
    }
```
Подмена ссылки вместо копирования. Благодаря этому поле `heap` в контроллере остаётся `final`, а FX-поток не занимается долгой сборкой.

```java
    public List<T> toList() {
        return Arrays.asList(Arrays.copyOf(items, size));
    }

    public int[] lastVisited() {
        return Arrays.copyOf(visited, visitedCount);
    }
```
Копии внутренних массивов: снаружи нельзя испортить сами массивы. Сами талоны при этом общие.

```java
    // Проверка рассчитана и на кучу, испорченную гонкой, поэтому null и неверный size не приводят к падению
    public boolean isValidHeap() {
        if (size > items.length) {
            return false;
        }
        for (int i = 0; i < size; i++) {
            if (items[i] == null) {
                return false;
            }
            if (i > 0 && comparator.compare(items[parent(i)], items[i]) > 0) {
                return false;
            }
        }
        return true;
    }
```
Проверка инварианта для тестов и демонстрации гонки.

```java
    private void ensureCapacity(int required) {
        int capacity = items.length;
        while (capacity < required) {
            capacity *= GROWTH_FACTOR;
        }
        if (capacity != items.length) {
            items = Arrays.copyOf(items, capacity);
        }
    }
```
**Рост массива в 2 раза.** Цикл нужен для `merge` и `addAll`: за один раз может понадобиться намного больше места. Удвоение стоит O(n), но случается редко, поэтому вставка в среднем остаётся дешёвой (амортизированная оценка).

| Операция | Сложность | Почему |
|---|---|---|
| `insert` | O(log n) | всплытие по высоте дерева |
| `peek` | O(1) | минимум в ячейке 0 |
| `extractMin` | O(log n) | погружение из корня |
| `find` | O(n) | номер карты не упорядочен |
| `delete` | O(log n) | по известному индексу |
| `topK` | O(k log k) | кандидатов не больше k+1 |
| `changePriority` | O(log n) | сдвиг в одну сторону |
| `merge` | O(n + m) | склейка и heapify |
| `replaceWith` | O(1) | подмена ссылки |

**Вопросы преподавателя**

**Почему именно куча, а не отсортированный массив?**
Вставка в отсортированный массив стоит O(n) из-за сдвига, в куче O(log n). Для очереди нужен только минимум, полная сортировка не нужна.

**Почему родитель `(i-1)/2`?**
Дети узла i лежат в `2i+1` и `2i+2`. Обратная формула для обоих даёт i, потому что целочисленное деление отбрасывает дробную часть.

**Куча отсортирована?**
Нет. Гарантия только между родителем и детьми. Отсортированную последовательность даёт повторный `extractMin`.

**Почему в `topK` нельзя просто пройти первые k ячеек массива?**
Массив кучи не отсортирован: второй по срочности может быть в ячейке 1 или 2, а третий глубже.

**Почему не `PriorityQueue`?**
Запрещено заданием в основном коде. `PriorityQueue` есть только в `src/test`, в бенчмарке.

**Что будет с индексами после `delete`?**
Меняются, поэтому индекс нельзя хранить между операциями. Программа берёт его заново: это номер строки таблицы или результат `find`.

**Как сделать поиск быстрее O(n)?**
Хранить вспомогательную таблицу «карта → индекс» и обновлять её при каждом обмене. Это усложнило бы код, а задание это не требует.

### 8.2 `SynchronizedTicketHeap.java` — защищённая версия

**Что делает.** Та же куча, но каждый публичный метод выполняется под монитором объекта: потоки входят строго по очереди.

```java
// Защищённая версия кучи: каждая операция идёт под монитором объекта, поэтому потоки выполняют их строго по очереди.
// Составное действие вроде find + delete не атомарно: между вызовами другой поток может изменить кучу.
public class SynchronizedTicketHeap<T> extends TicketHeap<T> {

    public SynchronizedTicketHeap(Comparator<T> comparator) {
        super(comparator);
    }

    @Override
    public synchronized void insert(T item) {
        super.insert(item);
    }
```
`synchronized` на методе: перед входом поток берёт монитор объекта `this`, остальные ждут. Остальные методы устроены так же. Наследование удобно тем, что `RaceDemo` работает с обоими вариантами через тип `TicketHeap`.

**Вопросы преподавателя**

**Почему основная очередь не использует этот класс?**
Её меняет только FX-поток, фоновые задачи работают с локальными данными. Синхронизация там ничего бы не защищала.

**Хватит ли `synchronized` только на `insert`?**
Для опыта со вставками да, но чтение `size()` без монитора могло бы увидеть устаревшее значение. Поэтому защищены все методы, это проверяет тест `everyPublicHeapMethodIsSynchronized`.

**Почему `find`, затем `delete` остаётся опасным?**
Каждый вызов атомарен, но между ними другой поток может сдвинуть элементы, и индекс устареет. Нужна синхронизация на всё составное действие.

### 9.2 `RaceDemo.java` — демонстрация гонки

**Что делает.** Запускает 8 потоков, каждый вставляет 50 000 чисел. Опыт идёт на двух кучах: обычной и `SynchronizedTicketHeap`. Очередь талонов не затрагивается.

```java
    public record Result(int expected, int actualSize, boolean validHeap, int failedInserts) {
        public boolean isCorrect() {
            return actualSize == expected && validHeap && failedInserts == 0;
        }
    }
```
Итог одного прогона. У record можно объявлять свои методы.

```java
    public static Result insertConcurrently(TicketHeap<Integer> heap, int threads, int insertsPerThread)
            throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1);
        AtomicInteger failedInserts = new AtomicInteger();
```
- `CountDownLatch` — защёлка: потоки ждут `await()`, пока главный поток не вызовет `countDown()`. Так они стартуют одновременно. Без неё первый поток успел бы закончить раньше, чем запустился второй, и гонки могло бы не быть.
- `AtomicInteger` — счётчик, безопасный для потоков: сам счётчик не должен страдать от той же гонки.

```java
                for (int value = insertsPerThread; value > 0; value--) {
                    try {
                        // Убывающие значения заставляют каждую вставку всплывать до корня и менять много ячеек
                        heap.insert(value * threads + threadNumber);
                    } catch (RuntimeException e) {
                        // Незащищённая куча может упасть на полпути: такой исход и показывает демонстрация
                        failedInserts.incrementAndGet();
                    }
                }
```
Это не проглоченное исключение: ошибка считается и попадает в отчёт.

```java
        start.countDown();
        for (Thread worker : workers) {
            worker.join();
        }

        return new Result(threads * insertsPerThread, heap.size(), heap.isValidHeap(), failedInserts.get());
```
`join()` — дождаться завершения потока. Читать результат можно только после всех `join`.

**Что ломается без защиты.** Пример одного запуска: в куче 113 649 элементов из 400 000, инвариант нарушен, 102 686 вставок упали с исключением. С `synchronized` всегда 400 000 и инвариант соблюдён.
- `size++` — это три действия: прочитать, прибавить, записать. Два потока читают одно значение, один элемент затирает другой.
- При удвоении один поток заменяет `items` новым массивом, а другой пишет в старый, и запись теряется.
- Всплытие сначала проверяет условие, затем меняет ячейки. Между этими шагами другой поток успевает изменить массив, и обмен ломает порядок.

**Вопросы преподавателя**

**Что такое гонка?**
Результат зависит от того, как чередуются потоки, работающие с общими данными. Если хотя бы один из них пишет, нужна синхронизация.

**Почему числа каждый раз разные?**
Чередование потоков определяет планировщик ОС. Поэтому порчу незащищённой кучи нельзя утверждать обычным тестом, она проверяется детерминированно, см. раздел 11.

**Почему `volatile` не помог бы?**
`volatile` делает запись видимой другим потокам, но `size++` останется тремя действиями и не станет атомарным.

## 10. Пакет `serialization` — форматы bin и JSON

### 10.1 `SerializationException` и `SerializationErrorCode` — ошибки файла

**Что делает.** Своё исключение с кодом, по аналогии с `CsvLoadException`.

```java
public enum SerializationErrorCode {
    BAD_MAGIC,
    UNSUPPORTED_VERSION,
    CORRUPTED_DATA,
    UNKNOWN_TYPE
}
```
- `BAD_MAGIC` — файл не наш;
- `UNSUPPORTED_VERSION` — версия файла не поддерживается;
- `CORRUPTED_DATA` — файл повреждён;
- `UNKNOWN_TYPE` — неизвестный тип талона.

```java
public class SerializationException extends Exception {
    private final SerializationErrorCode code;

    public SerializationException(SerializationErrorCode code, String message) {
        super(code + ": " + message);
        this.code = code;
    }
```
Проверяемое исключение. Код попадает и в текст сообщения для диалога, и в `getCode()` для тестов.

### 10.2 `Serializer` и `Serializers` — общий контракт

**Что делает.** `Serializer` описывает, что умеет любой формат. `Serializers` выбирает реализацию по расширению файла.

```java
// Общий контракт форматов. GUI и тесты работают с ним и не знают, что внутри файла.
// IOException означает сбой диска, SerializationException означает плохое содержимое файла.
public interface Serializer {
    void write(Path file, List<Ticket> tickets) throws IOException;

    List<Ticket> read(Path file) throws IOException, SerializationException;

    String extension();
}
```
Два разных исключения, потому что это разные ситуации. `write` не бросает `SerializationException`: записывает программа сама из проверенных данных.

```java
public final class Serializers {
    private static final List<Serializer> ALL = List.of(new BinarySerializer(), new JsonSerializer());
```
Единственное место, где перечислены форматы. Новый формат добавляется одной строкой, и фильтр в `FileChooser` появится сам.

```java
    public static Optional<Serializer> forFile(Path file) {
        String name = file.getFileName().toString().toLowerCase(Locale.ROOT);
        return ALL.stream()
                .filter(serializer -> name.endsWith("." + serializer.extension()))
                .findFirst();
    }
```
Stream: отфильтровать форматы и взять первый подходящий. `Locale.ROOT` — приведение к нижнему регистру не зависит от языка системы.

### 10.3 `BinarySerializer.java` — бинарный формат

**Что делает.** Пишет и читает собственный формат через `DataOutputStream` и `DataInputStream`.

```java
// Формат файла:
//   заголовок: magic (4 байта), версия (short), количество записей (int);
//   запись: код типа (byte), карта, ФИО, кабинет (UTF), срочность (byte),
//           время (long секунды и int наносекунды), адрес (UTF, только у HOME).
public class BinarySerializer implements Serializer {
    static final int MAGIC = 0x51554555; // Байты ASCII "QUEU"
    static final short VERSION = 1;
```
Формат описан прямо в коде. **Magic** — первые байты, по которым видно, что файл наш. `0x51 0x55 0x45 0x55` в таблице ASCII это буквы `QUEU`.

**Почему не `Serializable`?** Его формат привязан к именам классов и полей: после переименования старый файл не прочитается. Свой формат хранит только данные, файл меньше, а совместимостью управляет версия в заголовке.

```java
    @Override
    public void write(Path file, List<Ticket> tickets) throws IOException {
        try (DataOutputStream out = new DataOutputStream(
                new BufferedOutputStream(Files.newOutputStream(file)))) {
            out.writeInt(MAGIC);
            out.writeShort(VERSION);
            out.writeInt(tickets.size());
            for (Ticket ticket : tickets) {
                writeTicket(out, ticket);
            }
        }
    }
```
Потоки вложены друг в друга: `DataOutputStream` умеет писать числа и строки, `BufferedOutputStream` копит байты, `Files.newOutputStream` пишет в файл. Без буфера каждое число шло бы отдельным обращением к диску.

```java
    private void writeTicket(DataOutputStream out, Ticket ticket) throws IOException {
        out.writeByte(ticket.type().code());
        out.writeUTF(ticket.getCardNumber());
        out.writeUTF(ticket.getFullName());
        out.writeUTF(ticket.getRoom());
        out.writeByte(ticket.getUrgency());
        out.writeLong(ticket.getTakenAt().toEpochSecond(ZoneOffset.UTC));
        out.writeInt(ticket.getTakenAt().getNano());
        if (ticket.type() == TicketType.HOME) {
            out.writeUTF(ticket.getAddress());
        }
    }
```
- `writeUTF` пишет два байта длины, затем байты строки.
- Время хранится двумя числами. `ZoneOffset.UTC` нужен для пересчёта: при чтении используется тот же сдвиг, поэтому значение восстанавливается точно.
- Адрес только у `HOME`: при чтении код типа говорит, есть ли он.

```java
    @Override
    public List<Ticket> read(Path file) throws IOException, SerializationException {
        try (DataInputStream in = new DataInputStream(
                new BufferedInputStream(Files.newInputStream(file)))) {
            int count = readHeader(in);
            // Память под записи не выделяем заранее: в испорченном заголовке может быть огромное число
            List<Ticket> tickets = new ArrayList<>();
            for (int i = 0; i < count; i++) {
                tickets.add(readTicket(in, i + 1));
            }
            if (in.read() != -1) {
                throw corrupted("после последней записи остались лишние байты");
            }
            return tickets;
        } catch (EOFException e) {
            throw corrupted("файл обрезан");
        } catch (UTFDataFormatException e) {
            throw corrupted("испорчена строка");
        }
    }
```
- Читать надо в том же порядке, в каком писали.
- `in.read() != -1` проверяет конец файла: лишние байты тоже считаются порчей.
- `EOFException` — файл кончился раньше времени. Переводим его в понятную ошибку. Настоящие ошибки диска (`IOException`) проходят наружу без изменений.

```java
    private int readHeader(DataInputStream in) throws IOException, SerializationException {
        int magic = in.readInt();
        if (magic != MAGIC) {
            throw new SerializationException(SerializationErrorCode.BAD_MAGIC,
                    "Файл не является очередью талонов");
        }
        short version = in.readShort();
        if (version != VERSION) {
            throw new SerializationException(SerializationErrorCode.UNSUPPORTED_VERSION,
                    "Версия файла " + version + " не поддерживается, ожидается " + VERSION);
        }
```
Порядок важен: сначала признак, потом версия, и только потом записи. Формат записей зависит от версии.

```java
        try {
            LocalDateTime takenAt = LocalDateTime.ofEpochSecond(seconds, nanos, ZoneOffset.UTC);
            return type.create(cardNumber, fullName, room, urgency, takenAt, address);
        } catch (DateTimeException | IllegalArgumentException e) {
            throw corrupted("запись " + number + ": " + e.getMessage());
        }
```
Данные проверяются и при чтении, файлу доверять нельзя. `catch (A | B e)` — **multi-catch**: один обработчик на два типа исключений.

### 10.4 `TicketDto.java` и `JsonSerializer.java` — формат JSON

**Что делает.** Пишет `{"formatVersion": 1, "tickets": [...]}` через Jackson. Тип талона задаётся полем `type`.

```java
// Запись для JSON. Держит Jackson вне модели: ClosedTicket остаётся без сеттеров и конструктора по умолчанию.
// urgency имеет тип Integer, иначе пропущенное поле молча стало бы нулём, то есть самой высокой срочностью.
record TicketDto(String type, String cardNumber, String fullName, String room,
                 Integer urgency, LocalDateTime takenAt, String address) {

    static TicketDto from(Ticket ticket) {
        return new TicketDto(ticket.type().name(), ticket.getCardNumber(), ticket.getFullName(),
                ticket.getRoom(), ticket.getUrgency(), ticket.getTakenAt(), ticket.getAddress());
    }
}
```
**DTO** (data transfer object) — объект для передачи данных. Jackson работает с record, модель не содержит его аннотаций. Тип `type` строковый, иначе неизвестный тип дал бы общую ошибку Jackson вместо `UNKNOWN_TYPE`.

```java
    // Чтение строгое: хвост после документа и дробная срочность считаются порчей файла
    private static final ObjectMapper MAPPER = new ObjectMapper()
            .registerModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .enable(DeserializationFeature.FAIL_ON_TRAILING_TOKENS)
            .disable(DeserializationFeature.ACCEPT_FLOAT_AS_INT);
```
- `ObjectMapper` — главный класс Jackson. Он потокобезопасен, поэтому один на всю программу.
- `JavaTimeModule` учит Jackson работать с `LocalDateTime`.
- Без `WRITE_DATES_AS_TIMESTAMPS` дата пишется строкой `2026-09-24T10:30:00`, а не массивом чисел.
- Без `FAIL_ON_TRAILING_TOKENS` данные после закрывающей скобки молча терялись бы.
- Без `ACCEPT_FLOAT_AS_INT` значение `1.9` превратилось бы в `1`.

```java
    private record QueueFile(int formatVersion, List<TicketDto> tickets) {
    }

    @Override
    public void write(Path file, List<Ticket> tickets) throws IOException {
        List<TicketDto> records = new ArrayList<>(tickets.size());
        for (Ticket ticket : tickets) {
            records.add(TicketDto.from(ticket));
        }
        MAPPER.writerWithDefaultPrettyPrinter().writeValue(file.toFile(), new QueueFile(VERSION, records));
    }
```
Запись: переводим талоны в DTO и отдаём Jackson. `writerWithDefaultPrettyPrinter` добавляет отступы ради читаемости, это увеличивает файл.

```java
        JsonNode root;
        try {
            root = MAPPER.readTree(file.toFile());
        } catch (JsonProcessingException e) {
            throw corrupted("неверный синтаксис JSON");
        }

        // Сначала версия: в файле другой версии записи могут быть устроены иначе
        JsonNode version = root.path(VERSION_FIELD);
        if (!version.isInt()) {
            throw corrupted("поле " + VERSION_FIELD + " отсутствует или не целое");
        }
```
Чтение идёт через дерево `JsonNode`, а не сразу в объект: так версию можно проверить до разбора записей. `path` возвращает пустой узел вместо `null`, поэтому работает и для пустого файла. `JsonProcessingException` — наследник `IOException`, поэтому ловится отдельно: это порча файла, а не сбой диска.

```java

        TicketDto dto;
        try {
            dto = MAPPER.treeToValue(record, TicketDto.class);
        } catch (JsonProcessingException e) {
            throw corrupted("запись " + number + " не разобрана");
        }
        if (dto == null) {
            throw corrupted("запись " + number + " пуста");
        }
```
Перевод узла в record. Для `null` в массиве Jackson вернёт `null`, поэтому отдельная проверка.

```java
        if (dto.urgency() == null) {
            throw corrupted("запись " + number + ": нет срочности");
        }
```
Проверка, ради которой поле имеет тип `Integer`.

**Вопросы преподавателя**

**Что такое roundtrip?**
Записать и прочитать обратно: данные должны совпасть. Это главный тест сериализации, он идёт через интерфейс `Serializer` для обоих форматов.

**Как GUI выбирает формат?**
По расширению через `Serializers.forFile`. Контроллер работает с типом `Serializer` и не знает реализацию.

**Зачем версия в файле?**
Когда формат изменится, программа увидит старую версию и сможет сообщить об этом или обновить данные, а не прочитать мусор.

**Какой формат лучше?**
Зависит от задачи. На 10⁴ записях bin меньше в 3,52 раза (570 КиБ против 2008 КиБ) и быстрее примерно в 4–5 раз. JSON можно читать и править руками.

**Что будет при импорте битого файла?**
Диалог с кодом ошибки. Куча подменяется только в `onSuccess`, поэтому очередь не меняется.

```java

            "queue_bad_magic.bin,        BAD_MAGIC",
            "queue_wrong_version.bin,    UNSUPPORTED_VERSION",
```
**Параметризованный тест** — один метод с набором входных данных, каждая строка считается отдельным запуском. Файлы лежат в `src/test/resources` и читаются из classpath, поэтому тест не зависит от рабочей папки. Бинарные файлы собраны отдельным скриптом побайтово, поэтому тест проверяет сам формат, а не совпадение кода с самим собой.

```java

    @Timeout(30)
    void protectedHeapKeepsAllElements() throws InterruptedException {
```
Гонка недетерминирована, поэтому тест защищённой кучи повторяется 5 раз. `@Timeout` не даст ему зависнуть.

```java

    // и замер внутри сравнения, а второй за это время изменил кучу. Обмен первого портит инвариант
    @Test
    @Timeout(10)
    void staleSwapBreaksUnprotectedHeap() throws InterruptedException {
```
Порчу незащищённой кучи нельзя проверять обычным запуском: тест иногда проходил бы случайно. Здесь чередование задано защёлками: медленный поток останавливается внутри компаратора, основной вставляет элемент, затем медленный делает устаревший обмен. Результат одинаков при каждом запуске.

**Проверка самих тестов.** В код вносились искусственные поломки (мутации). Из 30 первых поломок 19 тесты не заметили, например пустой `copyFrom` и запись `CLOSED` как `TICKET`. После этого тесты усилены, а 8 важнейших поломок проверены повторно: все обнаруживаются.

### 11.3 `HeapBenchmark` и `FormatComparison` — замеры

Оба класса лежат в `src/test/java/benchmark`: задание требует, чтобы `PriorityQueue` не было в основном коде. Это обычные программы с `main`, а не тесты.

```java
    private static double medianMillis(Supplier<Runnable> prepare) {
        for (int i = 0; i < WARMUP_RUNS; i++) {
            prepare.get().run();
        }
```
**Прогрев.** JVM сначала интерпретирует код, а горячие места компилирует по ходу работы (JIT). Первые прогоны медленнее, поэтому они не считаются.

```java
        double[] times = new double[MEASURED_RUNS];
        for (int i = 0; i < MEASURED_RUNS; i++) {
            Runnable operation = prepare.get();
            long start = System.nanoTime();
            operation.run();
            times[i] = (System.nanoTime() - start) / NANOS_IN_MILLI;
        }
```
Подготовка данных идёт до старта таймера. Берётся медиана: она меньше страдает от случайных выбросов, чем среднее.

```java
    // Результат складывается сюда, чтобы компилятор не выбросил вычисления как ненужные
    private static long sink;
```
Если результат нигде не используется, JIT может удалить вычисление целиком.

**Главные выводы замеров.** `insert` наравне с `PriorityQueue`. `topK` не зависит от размера очереди и на 10⁵ быстрее в 2 раза. `find` и связанные с ним операции медленнее: записывается путь для подсветки. `merge` через heapify на 10⁵ не обогнал `addAll`: случайная вставка в кучу в среднем стоит O(1), и лучшая асимптотика проигрывает константе. Цифры приведены в отчёте ЛР2.

## 12. Как всё работает вместе (сценарии)

### Запуск
`Main.main` → `ClinicApplication.launchApplication` → `Application.launch` → JavaFX создаёт `ClinicApplication` и вызывает `start(stage)` → `new MainController(stage)` → `createView()` (таблица, панель, кнопки) → `stage.show()`.

### Добавление
Кнопка «Добавить» → `addTicket()` → `TicketDialog.showForCreate` → пользователь заполняет форму → `parseTicket` (число и дата) → `validate()` (пустые поля, `;`, диапазон 0–3, адрес) → при ошибке диалог показывается снова → при успехе `Optional.of(ticket)` → `heap.insert` → `refresh()` → строка в таблице, путь всплытия на панели.

### Редактирование и изменение приоритета
Выбор строки → слушатель включает кнопки только для `Editable` → `editTicket()` или `changePriority()` → диалог → `updateInHeap` → `heap.changePriority(индекс строки, изменение)` → изменение внутри операции кучи → `restore` сдвигает элемент → `refresh()` → выделение возвращается на тот же талон.

### Загрузка и слияние CSV
`FileChooser` → снимок очереди (для слияния) → `QueueTasks.loadCsv` в фоновом потоке → `CsvLoader.loadWithReport` с прогрессом → для каждой строки: пропуск заголовка и пустых → `split(";", -1)` → проверка 7 колонок → `parseInt` → `LocalDateTime.parse` → `TicketType.parse` → `create` с проверкой → хорошие строки в список, битые в список ошибок → `merged` собирает новую кучу → `setOnSucceeded` в FX-потоке → `applyLoaded` → `heap.replaceWith` → `refresh()` → предупреждение о битых строках.

### Сохранение CSV
`FileChooser` → снимок `heap.toList()` → `Task` → `CsvSaver.save` → заголовок → для каждого талона `toLine` → запись.

### Генерация
Кнопка → N → снимок очереди → `QueueTasks.generate` в фоне: `generator.next()`, `updateProgress`, проверка `isCancelled()` → `merged` → `onSuccess` в FX-потоке → `replaceWith` → `refresh()`. При отмене результат никуда не попадает, очередь прежняя.

### Экспорт и импорт
`FileChooser` с фильтрами → `Serializers.forFile` по расширению → `Task` → `serializer.write` или `serializer.read` → при импорте `heapOf` собирает кучу в фоне → `replaceWith` → `refresh()`. Битый файл → `SerializationException` → `setOnFailed` → диалог с кодом, очередь не меняется.

### Демонстрация гонки
Кнопка → `Task` → `RaceDemo.run` → 8 потоков на обычной куче → 8 потоков на защищённой → отчёт в диалоге.

## 13. Вопросы, которые может задать преподаватель

Вопросы по новым классам собраны в их разделах (5, 7, 8, 9, 10). Здесь общие.

**Что такое `static`?**
Член класса, а не объекта. Существует в одном экземпляре, вызывается через имя класса. Внутри static-метода нет `this`. Пример: `Dialogs.error(...)`, `Ticket.PRIORITY`, `main`.

**Что такое `final`?**
У поля/переменной — присваивается один раз. У класса — нельзя наследоваться (`ClosedTicket`, `CsvFormat`). У метода — нельзя переопределить. `final`-ссылка не делает объект неизменяемым — запрещает только переприсвоить ссылку.

**Почему `ClosedTicket` — `final`?**
Чтобы никто не унаследовался и не добавил сеттеры: гарантия «только чтение» держится и на отсутствии подклассов.

**Зачем приватный конструктор у `CsvFormat`, `Dialogs`, `TicketDialog`, `TicketTableFactory`, `QueueTasks`, `Serializers`?**
Это утилитные классы — только static-члены. Приватный конструктор запрещает создание бессмысленных объектов.

**Чем интерфейс отличается от класса?**
Интерфейс описывает контракт (какие методы должны быть), не хранит состояние объекта и не создаётся через `new`. Класс может реализовать много интерфейсов, но наследовать только один класс.

**Чем абстрактный класс отличается от интерфейса?**
Абстрактный класс хранит поля и готовые методы (`Ticket`), но объект его создать нельзя. Наследовать можно только один. Интерфейс (`Editable`, `Serializer`) задаёт только контракт.

**Что такое `@Override`?**
Аннотация: метод переопределяет метод родителя/интерфейса. Компилятор проверяет, что такой метод действительно есть.

**Что делает `super(...)`?**
Вызывает конструктор родителя, должен быть первой строкой конструктора.

**Где полиморфизм?**
`ticket.type()` и `ticket.getAddress()` вызываются у переменной типа `Ticket`, а работает версия реального класса. `serializer.write` работает для любого формата. `editable.validate()` у талона на дому проверяет ещё и адрес.

**Что такое обобщения (generics)?**
Параметр типа: `TicketHeap<Ticket>` хранит только талоны, ошибку типа поймает компилятор. Примитивы подставить нельзя, поэтому `TicketHeap<Integer>`, а не `TicketHeap<int>`.

**Checked и unchecked исключения?**
Checked (`IOException`, `CsvLoadException`, `SerializationException`) компилятор заставляет обработать или объявить в `throws`. Unchecked (`RuntimeException` и наследники: `NumberFormatException`, `IllegalArgumentException`) — не обязательно.

**Зачем своё исключение `CsvLoadException`?**
Чтобы передавать код ошибки (`CsvErrorCode`) и понятное сообщение, и чтобы компилятор требовал его обработку.

**Что такое try-with-resources?**
`try (ресурс) { }` — ресурс (файл) закрывается автоматически, даже при исключении.

**Зачем `-1` в `split(";", -1)`?**
Чтобы не терялись пустые колонки в конце строки (пустой адрес). Иначе получилось бы 6 колонок вместо 7.

**Что такое BOM (`\uFEFF`)?**
Невидимый символ в начале UTF-8-файлов из Excel/Блокнота. Удаляется, чтобы распознать заголовок.

**Что такое `record`?**
Короткий неизменяемый класс данных; компилятор сам создаёт поля, конструктор, аксессоры, `equals/hashCode/toString`. `LoadResult` нужен, чтобы вернуть из метода два списка.

**Что такое `enum`?**
Тип с фиксированным набором именованных значений (`CsvErrorCode`, `TicketType`). Безопаснее строк: опечатку поймает компилятор.

**Что такое `Optional`?**
Контейнер «значение есть или нет». Используется вместо `null` для результата диалога (отмена = `Optional.empty()`).

**Что такое лямбда и `::`?**
Лямбда — короткая анонимная функция (`event -> action.run()`). `files::loadCsv` — ссылка на существующий метод, сокращение лямбды.

**Что такое `ObservableList`?**
Список, который сообщает таблице о добавлении и удалении элементов. Здесь он хранит только копию кучи для показа.

**Что такое pattern matching `instanceof`?**
`if (t instanceof HomeVisitTicket h)` — проверка типа и приведение в одну строку; `h` уже имеет тип `HomeVisitTicket`.

**Какой поток что делает?**
FX-поток рисует окно и обрабатывает кнопки, менять интерфейс и основную кучу можно только в нём. Тяжёлая работа идёт в `Task`, в фоновом потоке, а результат возвращается в FX-поток через `setOnSucceeded`.

**Зачем отдельный `Main`?**
Если класс с `main` наследует `Application`, запуск без модулей падает с «JavaFX runtime components are missing». Отдельный класс-пускач это обходит.

### Слабые места (лучше знать заранее, если спросят «что можно улучшить»)

1. Экспорт и сохранение пишут прямо в выбранный файл. Если запись оборвётся (нет места на диске, закрыли окно), старое содержимое потеряно. Надёжнее писать во временный файл и затем переименовывать.
2. `writeUTF` не принимает строки длиннее 65 535 байт. Поле такой длины при экспорте в bin даст ошибку и обрезанный файл. В JSON этого ограничения нет.
3. Проверка полей запрещает `;`, но разрешает перевод строки. Ручная правка JSON с `\n` в ФИО пройдёт импорт, а после сохранения в CSV строка распадётся на две битые.
4. `find` работает за O(n) и записывает путь. Со вспомогательной таблицей «карта → индекс» поиск был бы O(1), но код усложнился бы.
5. Номера карт генерируются уникально только внутри сеанса: талон из файла может совпасть с уже сгенерированным, и `find` вернёт первый из них.
6. На 6 млн талонов извлечение вместе с обновлением таблицы занимает 103–113 мс, чуть больше порога в 100 мс. Обновление копирует весь массив в таблицу.
7. Сортировка таблицы отключена, поэтому отсортировать талоны по ФИО нельзя. Вернуть её можно через `SortedList` в фоне.
8. Причина ошибки в `SerializationException` не сохраняется: сообщение «запись 1 не разобрана» не называет поле.
